# 놓칠라 개발 규칙

모든 리포에 공통으로 적용됩니다.

## 1. 브랜치

| 브랜치 | 용도 | 직접 push |
|---|---|---|
| `main` | 배포되는 코드 | 금지 (PR만) |
| `develop` | 개발 통합 | 금지 (PR만) |
| `feature/*` | 기능 개발 | 자유 |
| `fix/*` | 버그 수정 | 자유 |

작업은 항상 `develop`에서 분기합니다.

```bash
git switch develop
git pull
git switch -c feature/matching-engine
```

브랜치 이름은 `feature/영문-짧은-설명` 형식으로 씁니다.
예: `feature/user-input-form`, `fix/age-boundary`

## 2. 커밋 메시지

```
<타입>: <무엇을 했는지 한 줄>
```

| 타입 | 쓰는 때 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작은 그대로, 구조만 변경 |
| `style` | 포맷·공백·세미콜론 |
| `docs` | 문서 |
| `test` | 테스트 |
| `chore` | 설정, 패키지, 빌드 |
| `data` | 제도 데이터 추가·검수 |

예시

```
feat: 연령·거주 조건 비교 규칙 구현
fix: 만 34세 경계값이 미충족으로 판정되던 문제 수정
data: 성남시 청년 제도 3건 검수 완료
```

## 3. Pull Request

1. 작업이 끝나면 `develop`으로 PR을 올립니다.
2. **리뷰어 1명 이상의 승인**을 받아야 병합할 수 있습니다.
3. PR 템플릿의 체크리스트를 채웁니다.
4. 병합 방식은 **Squash and merge**를 사용합니다.
5. 병합 후 브랜치는 삭제합니다.

PR이 너무 커지지 않게 합니다. 화면 하나, 기능 하나 단위로 올립니다.

## 4. 이슈

- 모든 작업은 이슈로 만들고, PR에 `closes #번호`를 적습니다.
- 라벨: `feature` `bug` `data` `docs` `infra`
- 담당자(Assignee)와 마일스톤(주차)을 반드시 지정합니다.

마일스톤은 개발 일정의 주차 마감일과 같게 둡니다.

| 마일스톤 | 마감 |
|---|---|
| 1주차 기획·설계 | 10/18 |
| 2주차 기본 기능 | 10/25 |
| 3주차 자격 판정 | 11/01 |
| 4주차 AI·통합 | 11/08 |
| 5주차 AWS 배포 | 11/15 |
| 6주차 통합 테스트 | 11/20 |
| 최종 발표 | 11/23 |

## 5. 절대 커밋하면 안 되는 것

- `.env` 파일
- LLM API 키 (Claude / Gemini)
- DB 접속 정보, RDS 비밀번호
- AWS 액세스 키, `.pem` 키 파일
- 실제 사용자의 개인정보

새 설정값이 필요하면 `.env.example`에 **키 이름만** 추가하고, 값은 팀 채널로 공유합니다.
실수로 키를 커밋했다면 즉시 팀에 알리고 해당 키를 폐기·재발급합니다.

## 6. 자격 판정 관련 규칙

이 프로젝트에서 가장 조심해야 할 부분입니다.

- **자격 판정은 규칙 코드로만 합니다.** LLM 응답으로 판정 결과를 정하지 않습니다.
- **검수(`review_status = reviewed`)가 끝난 제도만** 판정에 사용합니다.
- 조건이 불명확하거나 입력 정보가 부족하면 `ELIGIBLE`이 아니라 **`NEEDS_CHECK`** 로 분류합니다.
- 규칙 엔진을 수정하면 **경계값 테스트를 반드시 추가**합니다. (예: 상한이 34세일 때 34세와 35세)
- 모든 결과에는 공식 출처 URL과 확인일이 함께 나가야 합니다.

## 7. 리뷰할 때 보는 것

- 자격 판정 결과가 바뀌는가? 바뀐다면 테스트가 있는가?
- 공식 출처 없이 표시되는 정보가 있는가?
- 민감 정보가 LLM API로 불필요하게 전달되는가?
- API 응답 형식이 명세와 같은가?
