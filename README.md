# 처음 협업하는 분들을 위한 Git 안내

규칙 원문은 [`CONTRIBUTING.md`](.github/CONTRIBUTING.md) 에 있습니다.
이 문서는 **그 규칙을 실제로 어떻게 치면 되는지**를 순서대로 적은 것입니다.
혼자 쓰던 Git 과 여러 명이 쓰는 Git 은 다릅니다. 이 흐름만 지켜도 사고가 거의 안 납니다.

## 0. 용어 정리

| 말 | 뜻 |
|---|---|
| 브랜치(branch) | 코드의 평행 세계. 내 브랜치에서 뭘 해도 남의 코드는 그대로입니다 |
| 커밋(commit) | 변경 사항을 한 덩어리로 저장하는 것. 작업 일지의 한 줄 |
| push | 내 컴퓨터의 커밋을 GitHub 로 올리는 것 |
| pull | GitHub 의 최신 코드를 내 컴퓨터로 받는 것 |
| PR(Pull Request) | "내 브랜치를 합쳐 주세요" 라고 요청하는 것. 여기서 리뷰를 받습니다 |
| 병합(merge) | 승인된 PR 의 코드를 목적지 브랜치에 실제로 합치는 것 |
| 충돌(conflict) | 같은 줄을 두 사람이 다르게 고쳐서 Git 이 판단을 못 하는 상태 |

## 1. 브랜치 전략

브랜치는 세 층으로 나눕니다.

```
main        ← 배포되는 코드.         직접 push 금지
  ↑ PR
develop     ← 개발이 모이는 곳.      직접 push 금지
  ↑ PR
feature/*   ← 각자 작업하는 곳.      여기서만 작업
fix/*
```

**왜 이렇게 하나요**

- `main` 은 언제 봐도 돌아가는 상태여야 합니다. 발표 때 보여줄 코드입니다.
- `develop` 은 서로의 작업이 합쳐지는 곳입니다. 여기서 깨지면 전원이 멈춥니다.
- 그래서 작업은 **항상 내 이름이 붙은 브랜치**에서 합니다.

**브랜치 이름**

`feature/영문-짧은-설명` 또는 `fix/영문-짧은-설명` 형식입니다. 한글·공백은 쓰지 않습니다.

| 좋은 예 | 나쁜 예 | 이유 |
|---|---|---|
| `feature/user-input-form` | `feature/작업` | 뭘 하는 브랜치인지 모릅니다 |
| `fix/age-boundary` | `test`, `my-branch`, `sujin` | 사람 이름이 아니라 작업 이름을 씁니다 |
| `feature/policy-list-api` | `feature/fix-everything` | 한 브랜치는 한 가지만 합니다 |

## 2. 하루 작업 흐름

매번 이 순서 그대로 하면 됩니다. 1~7번이 한 작업의 전체 수명입니다.

### 1) 이슈를 먼저 만듭니다

GitHub 리포 → Issues → New issue → 템플릿 선택.
담당자(Assignee)와 마일스톤(주차)을 지정합니다. 이슈 번호(`#12`)를 기억해 둡니다.

> 작업을 이슈로 먼저 만드는 이유: 누가 뭘 하고 있는지 서로 보입니다.
> 같은 걸 두 명이 동시에 만들다 날리는 일을 막습니다.

### 2) 최신 develop 을 받아서 브랜치를 만듭니다

```bash
git switch develop      # develop 으로 이동
git pull                # 남들이 올린 최신 코드 받기
git switch -c feature/user-input-form   # 새 브랜치 만들고 이동
```

`git pull` 을 빼먹으면 **오래된 코드 위에서 작업**하게 되어 나중에 충돌이 납니다.
브랜치를 만들 때 이 두 줄을 먼저 치는 습관을 들이세요.

### 3) 작업하고 커밋합니다

```bash
git status              # 지금 뭐가 바뀌었는지 확인 (항상 먼저)
git add src/pages/InputForm.jsx     # 올릴 파일만 지정
git commit -m "feat: 사용자 정보 입력 폼 화면 추가"
```

`git add .` 는 바뀐 걸 전부 담습니다. 편하지만 `.env` 같은 걸 같이 올리기 쉽습니다.
**`git status` 로 확인한 뒤에만** 쓰세요.

커밋은 작게, 자주 합니다. "화면 하나 만들었다", "버그 하나 고쳤다" 정도가 한 커밋입니다.
하루 종일 작업한 걸 한 번에 커밋하면 리뷰가 불가능하고, 되돌릴 때도 통째로 날아갑니다.

### 4) GitHub 로 올립니다

```bash
git push -u origin feature/user-input-form   # 그 브랜치의 첫 push
git push                                     # 두 번째부터는 이것만
```

### 5) PR 을 올립니다

GitHub 에 가면 노란 띠로 "Compare & pull request" 버튼이 보입니다.

- **base 가 `develop` 인지 꼭 확인하세요.** GitHub 가 기본으로 `main` 을 고르는 경우가 있습니다.
- PR 템플릿의 체크리스트를 채웁니다. 빈칸으로 두면 리뷰어가 뭘 봐야 할지 모릅니다.
- 본문에 `closes #12` 를 적습니다. 병합되면 그 이슈가 자동으로 닫힙니다.
- 리뷰어를 지정합니다.

### 6) 리뷰를 받고 고칩니다

**승인 1명 이상**이 있어야 병합할 수 있습니다.
리뷰 의견이 오면 같은 브랜치에서 고쳐서 또 push 하면 됩니다. PR 을 다시 만들 필요 없습니다.

```bash
# 고치고
git add .
git commit -m "fix: 리뷰 반영 - 생년월일 입력 검증 추가"
git push
```

리뷰는 사람을 지적하는 게 아니라 코드를 같이 보는 일입니다. 받는 쪽도, 주는 쪽도 그렇게 봐 주세요.

### 7) 병합하고 정리합니다

**Squash and merge** 로 병합합니다. 내 브랜치의 커밋 여러 개가 `develop` 에 한 줄로 들어갑니다.
병합 후 브랜치는 삭제합니다 (버튼이 바로 나옵니다).

```bash
git switch develop
git pull                # 내 작업이 합쳐진 develop 받기
git branch -d feature/user-input-form    # 내 컴퓨터의 브랜치도 삭제
```

## 3. 커밋 메시지 규칙

```
<타입>: <무엇을 했는지 한 줄>
```

타입은 아래 중 하나입니다. 콜론(`:`) 과 공백을 꼭 넣습니다.

| 타입 | 쓰는 때 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작은 그대로, 구조만 변경 |
| `style` | 포맷·공백·세미콜론 |
| `docs` | 문서 |
| `test` | 테스트 |
| `chore` | 설정, 패키지, 빌드 |
| `data` | 제도 데이터 추가·검수 |

**쓰는 법**

- 한글로 씁니다. 타입만 영문입니다.
- **무엇을 했는지**를 씁니다. 파일 이름이 아니라 변화를 씁니다.
- 한 줄로 끝냅니다. 더 설명할 게 있으면 PR 본문에 씁니다.

| 좋은 예 | 나쁜 예 | 이유 |
|---|---|---|
| `feat: 연령·거주 조건 비교 규칙 구현` | `수정` | 뭘 수정했는지 알 수 없습니다 |
| `fix: 만 34세 경계값이 미충족으로 판정되던 문제 수정` | `fix bug` | 어떤 버그인지 알 수 없습니다 |
| `data: 성남시 청년 제도 3건 검수 완료` | `asdf`, `ㅁㄴㅇㄹ` | 나중에 이력을 못 찾습니다 |
| `chore: ruff 설정 추가` | `matcher.py 변경` | 파일 이름이 아니라 한 일을 씁니다 |
| `docs: API 명세에 /explain 추가` | `feat: 전체 작업` | 한 커밋은 한 가지만 담습니다 |

커밋 메시지는 3주 뒤의 자신과 팀원이 읽습니다. 그때 이해할 수 있게 씁니다.

## 4. 자주 겪는 상황

### push 했는데 거절당했습니다

```
! [rejected] develop -> develop (fetch first)
```

내가 작업하는 동안 남이 먼저 올렸습니다. 받아서 합친 뒤 다시 올립니다.

```bash
git pull
# 충돌이 나면 아래 "충돌이 났습니다" 참고
git push
```

### `main` 에 직접 push 하려니 막혔습니다

정상입니다. 규칙으로 막아둔 것입니다. 브랜치를 만들어 PR 로 올려 주세요.

### 충돌이 났습니다

같은 줄을 둘이 다르게 고쳤을 때 납니다. 파일을 열면 이렇게 보입니다.

```
<<<<<<< HEAD
const MAX_AGE = 34;
=======
const MAX_AGE = 39;
>>>>>>> develop
```

위쪽이 내 코드, 아래쪽이 받아온 코드입니다.
**둘 중 뭐가 맞는지 판단해서** 남길 코드만 두고 `<<<<<<<`, `=======`, `>>>>>>>` 세 줄을 지웁니다.
판단이 안 서면 **지우지 말고 상대방에게 물어보세요.** 특히 자격 판정 기준값은 혼자 결정하지 않습니다.

정리한 뒤:

```bash
git add 충돌난파일.jsx
git commit -m "chore: develop 병합 충돌 해결"
git push
```

### 브랜치를 안 만들고 develop 에서 작업해 버렸습니다

커밋 전이라면 그대로 브랜치를 만들면 됩니다. 변경 사항이 따라옵니다.

```bash
git switch -c feature/user-input-form
```

### 커밋 메시지를 잘못 썼습니다

**아직 push 안 했다면** 고칠 수 있습니다.

```bash
git commit --amend -m "feat: 올바른 메시지"
```

이미 push 했다면 그냥 두세요. Squash merge 할 때 PR 제목으로 정리됩니다.

### `.env` 를 커밋해 버렸습니다

**혼자 처리하지 말고 즉시 팀 채널에 알리세요.** 커밋에서 지워도 GitHub 이력에는 남습니다.
해당 API 키·비밀번호를 **폐기하고 재발급**하는 게 먼저입니다.

### 뭔가 잘못됐고 뭘 눌렀는지 모르겠습니다

`git reset --hard`, `git push --force` 는 **치지 마세요.** 남의 작업까지 날립니다.
지금 상태를 그대로 두고 팀에 물어보는 게 가장 빠릅니다. 커밋한 것은 거의 다 복구됩니다.

## 5. 절대 커밋하면 안 되는 것

- `.env` 파일
- LLM API 키 (Claude / Gemini)
- DB 접속 정보, RDS 비밀번호
- AWS 액세스 키, `.pem` 키 파일
- 실제 사용자의 개인정보

새 설정값이 필요하면 `.env.example` 에 **키 이름만** 추가하고, 값은 팀 채널로 공유합니다.

## 6. 자주 쓰는 명령어

| 하고 싶은 것 | 명령어 |
|---|---|
| 지금 상태 확인 | `git status` |
| 내가 어느 브랜치인지 | `git branch` |
| 브랜치 이동 | `git switch 브랜치이름` |
| 새 브랜치 만들고 이동 | `git switch -c feature/새-작업` |
| 최신 코드 받기 | `git pull` |
| 커밋 이력 보기 | `git log --oneline -10` |
| 내가 뭘 바꿨는지 보기 | `git diff` |
| 커밋 안 한 변경 되돌리기 | `git restore 파일이름` |

막히면 `git status` 를 먼저 쳐 보세요. Git 이 지금 상황과 다음에 뭘 하면 되는지 알려줍니다.
